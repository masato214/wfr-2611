## 目的

本線の migration を全部当てた DB で、**app のスキーマの security definer の関数 254 件のうち 146 件を、誰でも（PUBLIC）実行できる**（2026-11-20 切る段で数えた。数える SQL は下）。
security definer の関数は持ち主（migration を流す管理者）の権限で動くので、行の守り（RLS）を越えて読み書きできる。例：`app.agent_set_browser` は、呼べさえすれば、どの人の PC の値でも書ける。
決まり D-128.171（security definer の関数は、呼んでよい役だけに execute を渡し public から外す）は前からあり、関数ごとに `revoke all … from public` を書いて守ってきたが、書き忘れた 146 件が残った（関数ごとに人が思い出す守りは必ず漏れる・L-004）。

この葉は関数ごとに revoke を並べず、**根本を消す**：

1. **これから作る関数**：migration を流す役の既定の権限（`alter default privileges`）から PUBLIC の execute を外す。新しく作った関数は、初めから誰にも渡らない（呼ぶ役に渡すのは、今までどおり migration に `grant execute … to kaname_app` を書く）
2. **今ある関数**：app のスキーマの関数全部と、public のスキーマの security definer の関数 2 つ（0002 の `visible_scopes`・`has_permission`）から、PUBLIC を一度に外す。あわせて、持ち主・kaname_app・kaname_auth のほかの役に明示で渡した実行権（staging／本番の Supabase の anon・authenticated・service_role・手で作った kaname_ci_read など）と、migration を流す役の既定の権限でほかの役に渡す行も外す（呼んでよい役を 3 つに決め、それ以外は名前を挙げずに全部外す。Supabase の役の名前を決め打ちしない）
3. **呼ぶ役に要る物だけ渡す**：呼び手の権限で動く所（行の守り・呼び手の権限の関数と引き金の本文・アプリの文）が呼ぶ物で、まだ kaname_app に明示で渡していない 6 つだけを渡す
4. **戻らないことを試験で守る**：「PUBLIC と、決めた 3 つのほかの役が実行できる関数は 0 件」を DB の試験の行にする（検査の台本は足さない）

製品の振る舞いは変えない（今 kaname_app が呼んでいる関数は全部、後も呼べる）。

- **PostgreSQL の決まり**：スキーマを付けた `alter default privileges in schema app revoke … from public` は、全体の既定（関数は PUBLIC に execute）を外せない（スキーマごとの既定は全体の既定に足すだけ）。だから既定の権限はスキーマを付けずに書く（migration を流す役が作る全部のスキーマの関数に効く）
- **引き金の関数**：引き金が動くときには execute の権限を見ない（引き金を作るときだけ見る）。だから引き金の関数は誰にも渡さなくても動く。ただし **呼び手の権限で動く引き金（security definer でない）の本文が呼ぶ関数** は、呼び手（kaname_app）に execute が要る：`app.agent_notify_job()`・`app.agent_notify_conversation()` が `app.agent_notify_member(uuid)` を呼ぶ → ③ で渡す
- **行の守り（RLS）の式の中の関数** は、文を流した役（kaname_app）の権限で呼ばれる：`app.tenant_id()`・`app.user_id()`・`app.ops_grant_ok(uuid)`・`visible_scopes(uuid)`・`has_permission(…)` → ③ で渡す（ほかは明示の権限が在る）
- **security definer の関数の中から呼ぶ関数** は持ち主の権限で呼ばれるので、kaname_app に渡さなくても動く
- 試験はこのチケットを切る人が書き、実装する人は変えない（D-128.125）。実装の前に試験を流して赤を確かめない（D-128.143）
- migration の名前は時刻の形（K-327・作り手 gen_migrations.py は名前の順に並べる）。この葉は `20261120160000_function_execute_private.sql`（切る段で決めた）。先に作っている葉（K-354・K-355・K-365・K-366・K-371）の migration が後から入っても、名前の順に並ぶだけで、この葉と食い違わない：まっさらな DB では前の名前の物が先に当たり、この葉の ② が PUBLIC を外す。今ある DB では後に当たり、① の既定の権限で初めから PUBLIC に渡らない。どの葉の migration も新しい関数に `revoke all … from public` と `grant execute … to kaname_app` を書いている（切る段で 4 本を読んで確かめた）

- **呼んでよい役は 3 つ**：持ち主・`kaname_app`・`kaname_auth`。kaname_auth の明示の権限（K-52 などが渡した 16 件）は触らない（app のスキーマの usage が無いので今も呼べないが、前のチケットの決めを変えない）

```sql
-- ① これから作る関数：migration を流す役の既定の権限から PUBLIC の execute を外す（スキーマを付けない）
alter default privileges revoke execute on functions from public;
-- ② 今ある関数：app の関数全部と、public のスキーマの security definer の関数 2 つから PUBLIC を外す
revoke execute on all functions in schema app from public;
revoke execute on function public.visible_scopes(uuid), public.has_permission(uuid, text, uuid, text) from public;
-- ②b 持ち主・kaname_app・kaname_auth のほかの役に渡した実行権も外す（今ある関数と、migration を流す役の既定の権限の両方）。
--     staging／本番の Supabase の役や手で作った役に当たる。手元と CI の DB には該当が無く何もしない
do $$
declare r record;
begin
  for r in
    select distinct p.oid::regprocedure as f, a.grantee::regrole as g
      from pg_proc p cross join lateral aclexplode(p.proacl) a
     where (p.pronamespace = 'app'::regnamespace
            or (p.pronamespace = 'public'::regnamespace and p.prosecdef
                and not exists (select 1 from pg_depend d
                                 where d.classid = 'pg_proc'::regclass and d.objid = p.oid and d.deptype = 'e')))
       and a.grantee <> 0 and a.grantee <> p.proowner
       and a.grantee not in ('kaname_app'::regrole, 'kaname_auth'::regrole)
  loop
    execute format('revoke execute on function %s from %s', r.f, r.g);
  end loop;
  for r in
    select distinct d.defaclnamespace as ns, a.grantee::regrole as g
      from pg_default_acl d cross join lateral aclexplode(d.defaclacl) a
     where d.defaclrole = current_user::regrole and d.defaclobjtype = 'f'
       and a.grantee <> 0 and a.grantee <> d.defaclrole
       and a.grantee not in ('kaname_app'::regrole, 'kaname_auth'::regrole)
  loop
    if r.ns = 0 then
      execute format('alter default privileges revoke execute on functions from %s', r.g);
    else
      execute format('alter default privileges in schema %s revoke execute on functions from %s', r.ns::regnamespace, r.g);
    end if;
  end loop;
end $$;
-- ③ 呼び手の権限で動く所が呼ぶ物で、まだ kaname_app に明示で渡していない物だけを渡す
grant execute on function app.tenant_id(), app.user_id(), app.ops_grant_ok(uuid), app.agent_notify_member(uuid),
  public.visible_scopes(uuid), public.has_permission(uuid, text, uuid, text) to kaname_app;
```

## リスクと懸念

- **staging／本番（Supabase）の役**：Supabase は public のスキーマに作った関数を anon・authenticated・service_role に既定で渡す（Supabase の既定の権限・PUBLIC と別の行）。② の PUBLIC の revoke だけでは残り、public の `visible_scopes`・`has_permission` が Data API（PostgREST）から anon で呼べる恐れがあった。だから ②b で「持ち主・kaname_app・kaname_auth のほかの役」を名前を挙げずに全部外す。手元の CI の DB に Supabase の役は無いので、CI では K426-DB-013・014 が同じ形を作って見て、staging では K426-DB-012 で人が数える
- ②b は migration を流す役（Supabase では postgres）の既定の権限から、ほかの役に関数を渡す行を外す。Supabase の画面（Studio）の SQL や Supabase の部品（Auth・Storage・Realtime）は自分の役（supabase_admin など）で動き、この葉の関数を使わない。製品は Supabase の Data API も supabase-js の DB の口も使わない
- ① は migration を流す役が作る **全部のスキーマ** の関数に効く。今後 migration で拡張を足すと、その拡張の関数も初めは持ち主だけが呼べる（kaname_app で使うなら `grant` が要る）。足せば kaname_app の試験が `permission denied` で赤になるので、黙っては壊れない。共通の決まりへの 1 行（「関数の execute は既定で誰にも渡らない・呼ぶ役に migration で grant する」）はまとめ役に頼む
- 同じ決まり D-128.171 の残り半分（security definer の関数の search_path に pg_temp を入れる）は、app と public の security definer 256 件のうち 149 件に無い（`search_path=public, app` のまま）。この葉の範囲の外（類は同じだが直しが別・関数ごとに作り直しが要る）。PM に出して別の葉にする
