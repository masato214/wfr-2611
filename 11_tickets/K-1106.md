## 目的

DB が失敗したとき（問い合わせが例外・接続できない・取引が落ちた）の口の答えを、段を問わず **503 E-PAGE-003**（「いま使えません」・中身を返さない）にそろえる。
共通の決まり D-136.1（守りの判定が内部の不具合で判定できないときは 503 E-PAGE-003 で止める側に倒す）と同じ側にする PM の決め（控え帳 2026-11-22 18:30 を、11-23 に「段を問わず」に広げた）。

今の本線には 500 で返す所が残っている：

1. 口の中で DB の失敗を受けて **500 と E-PAGE-003** を返す所（F1 の認証の口・F5 の承認の decide.ts）
2. 口の中で受けずに投げた DB の例外が app.ts の onError まで落ちて **500（code null）** になる所（例：K234-API-012 の読む口の中の `1 / 0`・チケットを作る途中の知らせの書き込み・PC の印の受け取り）
3. 契約（`05_flow/screen_api.py` → `08_api/endpoints.json`）の outputs に `status: 500` の E-PAGE-003 が 9 口（EP-024・025・026・027・029・032・034・035・036）

PM の決め（作り方・2026-11-23）：

1. 1 は各口のその行を 503 に直す（文と中身を返さないのは今のまま）
2. 2 は契約の口の入口（`contract/op.ts` の `op()` が返す関数・要求の取引 inRequest の外側。中の取引は例外で戻ってから受ける）で受ける：投げられた例外が **DB の失敗**（SQLSTATE を持つ DB の例外か、DB に繋がらない・接続の取得が時間切れ）なら 503 E-PAGE-003 を返し、ログは口の名前と例外の種類だけ。入力が DB の決まりに合わない例外（22P02 ほか・dbInputFailure）は今のまま 422、DB でない例外（プログラムの誤り）は今のまま onError の 500
3. app.ts の onError は変えない（契約の外の口・DB でない例外の受け。app.ts は K-420・K-421・K-422 が作っている途中）
4. 管理者に頼む（admin-recovery・EP-025）とメールの確認（verify-email・EP-032）は、この葉では直さない（下の「やらないこと」）
5. ほかの葉が作っている途中の物は触らない：`ticket-update/update.ts`・`05_flow/screen_api.d/K-387.py`・`progress.test.ts`（K-440・K-564・K-583 が 503 にしている）、`approve-complete/complete.ts`・`approve-complete-complete.test.ts`（K-566 が 503 にしている）、K-477 の見えるグループの確かめ（K-477 の枝にだけ在る）。この葉の静的の試験は、持ち主が別の葉の物と、やらないことの 2 口を外して数える

## リスクと懸念

- 口の中の catch（この葉で 503 にした 9 か所）はどんな例外も受けるので、そこでは DB でない例外も 503 になる（今までも 500 E-PAGE-003 で受けていた所。入口の受けの「DB でない例外は 500」は、口の中で受けない例外にだけ効く）
- 入口の受けの「SQLSTATE を持つ DB の例外」には、SQL の誤り（列が無い など）や DB の関数の raise も入り、503 になる（DB の側の失敗として同じに扱う）

- 入口の受けは契約の口だけ。契約の外の口（auth/agent.ts ほか素の道すじ）の DB の例外は onError の 500 のまま（app.ts は作っている途中の葉が 3 本ある。それが入った後に別の葉で見る）
- 作っている途中のほかの葉で、DB の例外を受けずに投げて 500 を期待する試験があれば、この葉が入った後にその葉の CI で 503 になる（K-477 の見えるグループの確かめは 503 にする向き）
