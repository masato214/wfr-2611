## 目的

代表の答え（問い 33・answer=3d444fc8d59f・D-148.51）：**招待のリンクで新しく入る人のメールを確かめる。確認のメールを押すまで参加は決まらない**（勧め (a)「すぐ入れる」と違う）。K-421 が作った「宛てのメールを持たない招待（リンク）」で、ログインしていない新しい人が参加する道をこの葉が持つ：

- 参加を押す（acceptInvitation・ログインしていない・体 `{ name, password, email }`）→ **その時点では認証の利用者も所属も作らない**。保留の行（`kaname_auth.invitation_link_joins`）を置き、入れたメールに確認のメールを 1 通送る（関門 C6）。答えは 202 `{ data: { state: "sent", email: <伏せたメール> } }`
- 確認のリンク（`<webBaseUrl>/invite/confirm/<token>`）を開いた画面が確認の口（`POST /api/v1/auth/invitations/confirm`・`confirmInvitationJoin`・体 `{ token }`）を呼ぶと、そのときに認証の利用者（メールは確かめ済み）・所属・招待を使った印を作り、ログインの印を返す（201 `{ data: { token, workspace_id, next: "/mfa-setup" } }`・K-332 の acceptInvitation と同じ渡し方）

こうすると、ほかの人のメールを入れて押しても、確認のメールを押すまでアカウントは無い。メールの本当の持ち主は後から自分で登録・参加できる（放っておかれた保留の行は持ち主を止めない）。ログイン中の人の参加（自分の確かめたメールのアカウント）は K-421 のまま。メールで招いた招待（宛てのメールが届いた）は K-332 のまま。

## 前提と制約

分類: INV, REG, MAIL, AUTH

- **K-421 に依存**：K-421 が invitations.email の空を許し、accept.ts に「宛てのメールが空の招待・ログインしていない人は 401」の枝を置く。この葉はその枝を「保留の行と確認のメール・202」に替える（同じ accept.ts）
- **保留の行**：`kaname_auth.invitation_link_joins`（認証の接続だけが触る・kaname_app には渡さない。前からの保留の申し込み `kaname_auth.pending_signup`・0022 と同じ置き場と形）。列：id・invitation_id（public.invitations）・tenant_id・email（normalizeEmail でそろえた物）・display_name・pw_iv／pw_tag／pw_data（パスワードを鍵で包んだ物）・token_hash（確認のリンクのトークンの sha256）・expires_at（24 時間）・sent_at・send_error・confirmed_at・deleted_at・created_at・updated_at。同じ招待・同じメールの待っている行は 1 つ（部分の一意の索引 `(invitation_id, email) where confirmed_at is null and deleted_at is null`）。押し直したら同じ行のトークンと期限を替えて送り直す（前の確認のリンクは使えなくなる）
- **パスワードは平文で持たない**：前からの保留の申し込みと同じく、master key から導いた鍵で包む（packages/auth/src/pending.ts の `seal`・`open_`）。用途ごとに鍵を分けるため `seal`／`open_` に用途の引数（既定は今の "pending-signup"・この葉は "invitation-link-join"）を足す。**指示の「password_hash」にしなかった訳**：確認のときに作る利用者は前からの `createInvitedUser`（平文のパスワードを受けてハッシュにする）で作るので、ハッシュで預かると認証の部品に「ハッシュのまま利用者を作る」新しい口が要る。包む形は登録で使っている形のまま
- **確認のメール**は関門 C6（F2 の deps の mailer・server.ts の 1 か所）で送る。件名「【Kaname】{ワークスペース名} への参加を確かめてください」。本文は名前・ワークスペース名・招いた人の名前・確認のリンク・「24 時間で切れます」・「心当たりが無ければ、このメールは捨ててください（何も起きません）」だけ。パスワード・リンクの招待のトークンは書かない。送れたか（sent_at）・送れなかったか（send_error）を保留の行に書く（G-15：送れていないのに「送りました」と出さない）
- **答えのメールは伏せる**：202 の email は先頭 2 字・* を 4 つ・@ の後（`ki****@engine-base.example`。画面の葉 K-423 の試験の偽の答えと同じ形）。ログにメール・パスワード・トークンを出さない（宛先は mailTag の印・TP-REG-14）
- 同じ招待・同じメールで参加を同時に 2 回押したとき：`putLinkJoin` は `insert … on conflict (invitation_id, email) where confirmed_at is null and deleted_at is null do update set token_hash = excluded.token_hash, expires_at = excluded.expires_at, pw_iv = …, pw_tag = …, pw_data = …, display_name = …, sent_at = null, send_error = null, updated_at = now()` の 1 文（select してから insert にしない・一意の違反の 503 を出さない）。2 本とも 202・保留の行は 1・確認のメールは 2 通で、行に残った新しい方のトークンだけが使える（K422-API-030）
- 参加の順（ログインしていない・リンクの招待）：トークンの形 → 招待の様子（無い 404・取り消し／期限切れ／使われた 410）→ 止められたワークスペース 403・E-AUTH-012 → 名前（E-VAL-007）→ パスワード（E-VAL-005・026・漏れの照合）→ メール（空の字 ""・空白だけ・形違い → 422・E-INV-013 欄 email＝契約の pattern と同じ決まり／送られていない → 409・E-INV-016（conflict）・欄なし＝招待の行で決まる断り・控え帳 2026-11-20 16:51）→ そのメールにもうアカウントがある → 409・E-INV-006（ログインしてから参加）→ 保留の行を置く（S1）→ 確認のメール（S2）→ 送った印（S3）→ 202
- 確認の順：トークン（無い・空・空白だけ → 422・VALIDATION_ERROR。前後の空白を落として見る。空白だけは契約の決まり VALUE_RANGES の pattern `\S` で書く（K-355 の request_ref と同じ書き方）。UNEXPRESSIBLE_422 には足さない＝検査の例外を足さない・代表の答え answer=431fc50df51b）→ 保留の行に **印を付ける**（`update … set confirmed_at = now() where token_hash = $1 and confirmed_at is null and deleted_at is null and expires_at > now() returning …`。期限切れの行には印を付けない。同時に何回押しても 1 回だけ取れる）→ 0 行のときは同じ token_hash の行をもう 1 回読んで見分ける：行が無い・閉じた（deleted_at）→ 404・E-INV-001／もう印がある → 410・E-INV-015／期限切れ → 410・E-INV-014 → 招待の様子（使われた 410・E-INV-004・取り消し 410・E-INV-002・期限切れ 410・E-INV-003）・止められたワークスペース 403・E-AUTH-012・そのメールにもうアカウント（確認までの間に登録した）409・E-INV-006（どれも印を戻さずに保留の行を閉じる＝deleted_at）→ 包んだパスワードを開く → 利用者を作る（S4・createInvitedUser・メールは確かめ済み）→ 受諾（S5・app.accept_invitation の 1 取引）→ セッションを作る（S6）→ 201 `{ data: { token, workspace_id, next: "/mfa-setup" } }`
- 確認の失敗の分け方：**受諾（S5）が「使われた／取り消し／期限切れ」で断ったら**（別々の 2 人が同時に確認した競りで、相手が先に招待を使った など）、作った利用者を id で消し、**印を戻さず保留の行を閉じて** 410（E-INV-004・002・003）。それ以外の S4・S5 の失敗だけ、作った利用者を消して印を戻し 503（もう一度押せる）。S6（セッション）が落ちたら K-332 と同じく参加は取り消さない：503・E-PAGE-003・利用者と所属は残り印も付いたまま（押し直すと 410・E-INV-015「ログインして入ってください」・パスワードでログインできる・K422-API-029）
- **確認の口は冪等の器を使わない**（2 回目にログインの印を渡すと、リンクを持つ人なら誰でも入れてしまう・K-52 と同じ）。NO_GENERIC_409 に足す
- 同じリンクに別々のメールの保留の行が何本あってもよい（リンクは「持っている人なら誰でも 1 回」）。最初に確認した 1 人が招待を使い、ほかの人の確認は 410・E-INV-004
- 入った直後は今のまま「付けるまで進めない」（/mfa-setup・K-308）
- F2 の deps の config に `secretsMasterKey` を足す（登録の deps と同じ値。`apps/api/src/hooks/invitations.ts` の deps を組む所で `d.config.secretsMasterKey`（HookDeps の config に在る）から渡す）

## 外に影響する手順

- S1: 保留の行を書く（認証の接続・1 文。失敗したら何も残らない・K422-API-021）
- S2: 確認のメールを送る（関門 C6）[残る] — 送ったメールは取り消せない。送れなければ保留の行は残し、送れなかった印（send_error）を書いて 202・state failed（押し直せば同じ行のトークンを替えて送り直す・K422-API-022）
- S3: 送った印を保留の行に書く（S2 の後片付け）。落ちたら 1 回だけやり直し、それでも落ちたらログに 1 行で答えは変えない（S3 の失敗と S2 の後片付けの失敗を 1 行で見る・K422-API-023）
- S4: 確認のときに認証の利用者を作る（createInvitedUser）[残る] — 作った利用者は、続く受諾が落ちたら id で消す。S4 そのものが落ちたら印を戻して 503（何も残らない・K422-API-024）
- S5: 受諾（所属・グループ・規約の同意・出来事・招待を使った印）を DB に書く（app.accept_invitation の 1 取引）。失敗したら S4 の利用者を消し、印を戻す（K422-API-025）。受諾が「使われた・取り消し・期限切れ」で断ったら利用者を消し保留の行を閉じて 410（競り・K422-API-028）。後片付けも落ちたらログに 1 行（K422-API-026）
- S6: セッションを作る（kaname_auth.session と sessions に書く・openSessionFor）— 失敗しても参加は取り消さない（K-332 と同じ）。残る利用者と所属は確認で決まった正しい結果で、片付ける物ではない（後片付けは無いので [残る] は付けない）。503・E-PAGE-003・利用者と所属は残り、確認の印は付いたまま。押し直すと 410・E-INV-015（ログインして入ってください）で、パスワードでログインできる（K422-API-029）
