## 目的

棚を書ける人が、公開済みのページに「必ず守る」の印を付け外しする口 1 本と、上限の設定の表を作る（契約は K-675 が宣言済み・今は 501）：`setKnowledgeMust`（PUT /api/v1/knowledge_pages/:id/must・入力 `{ must }`・200 `{ id, must, used, limit }`）。入力・答え・断りは土台 2・3.2・4 章。

- **上限は 会社 30・グループ 20（グループごと）・個人 10（本人ごと）**。数は DB の設定の表 `knowledge_limits` の行で持ち、運営が後から行を直して変える（会社の管理者が変える画面は作らない）
- **付けられるのは、公開済みで本文が 2,000 字までのページ**。字数が合わなければ 409 E-KNW-061・上限に届いていれば 409 E-KNW-060（体に**今付いているページの一覧**を `detail` で返す＝画面の上限の小窓がそのまま出す）
- 外すのはいつでも（承認待ちの間を除く）。付け外しは証跡に残す
- 書く人は棚で決まる（切り方 0.3）：会社の棚＝管理者／グループの棚＝そのグループのマネージャー／自分の棚＝本人。見えない物は 404・見えるが書けないは 403
- この葉は **K-677 が分けて置いた `page-parts/act-must.ts` の中身を差し替え**、ページを読むと帯の操作に「必ず守るを付ける／外す」が出るようにする

- **口は 1 つの取引（`withTenant`）の中で、確かめてから関数を呼ぶ**：①`app.kpage_visible(id)` が偽→404（体は `{ error, code }` だけ）②`app.kpage_writable(id)` が偽→403 ③ページがまだ書き終えていない（`state = 'draft'`）→409 E-KNW-010 ④すでに同じ印なら 200（変えない・証跡なし・次の⑤を見ない）⑤`hasPendingRequest`（K-681）が真→409 E-KNW-011 ⑥`select app.kn_must_set($1, $2)`：`too_long`→409 E-KNW-061・`full`→409 E-KNW-060（体は `{ error, code, detail: { shelf_name, limit, pages } }`・控え帳の「409 は欄・details を付けない」は守り、差し込む値は `detail`）・`draft`→409 E-KNW-010・`denied`→403。**確かめで断る前に何も書かない**
- **答え**：200 `{ id, must, used, limit }`（鍵ちょうど 4・`used` は印を変えた後のこの棚の数・`limit` は今の設定）。付け外しとも同じ形
- **設定の行を直したら次の呼びから効く**（キャッシュしない）。上限を今の数より下げても、すでに付いているページは外れない（新しく付けるときだけ 409 E-KNW-060・外すのは通る）
- **付けたページが後から 2,000 字を超える**：書き終える口（K-680）が 409 E-KNW-041 で止める。この葉は公開済みの最新の版の字数で判定する（下書きの版は見ない）
- **移した先の数**：上の棚に上げる（K-688）で必ず守るのページが移るときの数と印の扱いは K-688 が決める（申し送り）
- **DB の失敗の言葉 → 番号**：`23514`（check 違反＝下書きのページに付けようとした）→409 E-KNW-010。**それ以外の例外は 503 E-PAGE-003**（何も書かない・ログに例外の種類だけ・題名を出さない）
- **証跡**：同じ取引で `app.record_audit(action, 'knowledge_pages', <ページの id>, 'C2', '{}')`。action は 付ける＝`knowledge.must.on`・外す＝`knowledge.must.off`。**印が変わったときだけ**残す。題名を入れない。断った操作・何も変わらない操作・落ちた操作には残さない
- **権限の波及**：マネージャーの役を外された・グループを抜けた・付けられた直後も、次の操作から今の所属で決まる（毎回 DB の関数が決める）
- 外へ出ない：メールもお知らせも出さない。AI も呼ばない。ログに題名を出さない

### 帯の操作の差し替え（page-parts/act-must.ts）

K-677 は `page-parts/act-must.ts` を「`mustActs(p)` が `[]` を返す」形で置いた。この葉が中身を差し替える（`read.ts`・`index.ts` を直さない）：

- `mustActs(p: PagePartCtx): Promise<PageAct[]>`：**書ける人**（`p.writable`）で、ページが**公開済み**で、**承認待ちの頼みが無い**（`hasPendingRequest`）ときだけ、`is_must` が真なら `["must-off"]`・偽なら `["must-on"]`。それ以外は `[]`
- **本文が 2,000 字を超えて付けられないページ（`must_blocked: "too_long"`）にも `"must-on"` を返す**（画面が押せない形にして訳を文にするため。押したときは口が 409 E-KNW-061）
- 自分の試験に「ページを読むと操作が出る」行を足してある（K685-API-018）

## リスクと懸念

- **製品共通の設定の行（`knowledge_limits`）を書き換える試験は K685-API-006 だけ**。ほかの試験ファイルが並べて流れているとき、その間だけ group の上限が変わる（K-714・K-697 など、この表に頼る後ろの試験が既定の数を前提にしないこと）。`finally` で必ず戻す（G-10）。後ろの葉が設定の行を使う試験を足すときは、数を決め打ちせず `app.kn_must_limit` を読む
- 上限の数え方は棚ごとに高々 30 行の走査。グループが多い会社でも 1 棚の数え方は変わらない。錠の鍵は棚ごとなので別の棚の付け外しは待たない（K685-API-005 の別の棚の行が見る）
- `security invoker` の関数は呼ぶ人の行の守りで数える。書ける人は棚の公開済みページを全部読めるので数え漏れは起きないが、行の守りを K-674 が直すとき（読める条件を狭める）この数え方に影響する。K685-DB-002 が見る
- `knowledge_limits` は会社の列を持たない新しい種類の表。場合表（`access-matrix.json`）・目録の自動検査が新しい表の行を求める。作る段で求められたら `changes-add` で足す（上の前からの試験の節）
- 見込みが 1 時間ぎりぎり（migration・口・帯の操作・試験 21 行）。超えるなら「帯の操作の差し替え」を別の葉に分ける（番号はまとめ役が決める）
