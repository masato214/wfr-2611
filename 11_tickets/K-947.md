## 目的

運営が別の会社を触る道は **security definer の関数だけ**（BYPASS は使わない・D-156.3）。段 13 の運営の口の葉（K-963〜K-995）が、どれも同じ形で関数を書けるように、型と土台と検査を先に置く。

- **関数の中の 2 層目**：入口（op.ts の役とできること）が抜けても、関数の頭で `app.ops_require(<できること>)` が運営の人とできることを確かめる（G-02）。指す会社は `app.ops_target(<会社>)` で、在る顧客のワークスペースだけに絞る（運営の会社・作りかけ・消した会社は「無い」）
- **書く関数は運営の記録を必ず書く**（運営と会社の両方・D-128.108）：`app.record_ops_audit` を中で呼ぶ
- **検査 `ops_definer_gate.py`**：migration の中の `app.ops_*` の security definer の関数が、①頭で ops_require を呼ぶ ②書くなら record_ops_audit を呼ぶ、を機械で見る（人が思い出さなくても漏れない・choke-points.md）
- **口から呼ぶ TS の土台**（`apps/api/src/features/F12/ops/db.ts`）：運営の文脈の 1 つの取引（opsTx）・記録の呼び口（opsAudit）・DB の断りを口の答えに直す（opsErrorReply：42501 → 403・P0002 → 404・ほか → 503 E-PAGE-003）

## 前提と制約

分類: TOOL, PERM

- 運営の文脈は K-944・K-1001 の形：role ops・tenantId null・userId は運営の会社の members.id。関数は `app.role()`・`app.user_id()` で確かめる（引数で人を受けない）
- `app.ops_require(p_cap text) returns uuid`（security definer・stable）：`app.role() = 'ops'` で、`ops_members` の `member_id = app.user_id()`・`revoked_at is null`・`deleted_at is null` の行があり、`p_cap = 'any'` か `p_cap = any(caps)` なら、その行の id。ほかは `raise exception … using errcode = 'insufficient_privilege'`（42501）
- `app.ops_target(p_tenant uuid) returns uuid`（security definer・stable）：`tenants` に在り、`deleted_at is null`・`half_made_at is null`・`id <> app.ops_tenant_id()` なら同じ id。ほかは `errcode = 'no_data_found'`（P0002）。中で ops_require は呼ばない（呼ぶ側が先に呼ぶ）
- 運営の関数の名前は `app.ops_<名前>`（検査はこの名前で見つける）。検査の台帳 `EXEMPT`（名前 → 理由）に、型でない前からの関数と、ログインの前に呼ぶ関数を置く：`app.ops_tenant_id`（定数）・`app.ops_grant_ok`（行の守りの中の判定）・`app.ops_plan_proposal_guard`（引き金）・`app.ops_require`・`app.ops_target`（この葉の型そのもの）・`app.ops_login_check`（K-944・ログインの前）・`app.ops_setup_consume`（K-945・ログインの前）
- 検査の読み方：`packages/db/migrations/*.sql` を名前の順に読み、`create [or replace] function app.ops_…` から `$$ … $$` の本体までを 1 つと数え、同じ名前は後の版で上書き。`security definer` が無い関数は見ない。本体の最初の文（`begin` の後・`declare` は除く）が `perform app.ops_require(` か `:= app.ops_require(` でなければ誤り。本体に `insert into`・`update `・`delete from` があり `app.record_ops_audit(` が無ければ誤り。誤りは「<ファイル名>: <関数名> …」の 1 行
- 断る番号（控え帳・D-156.12・D-156.17）：できることが無い＝403 FORBIDDEN、指した会社が無い・見えない＝404 NOT_FOUND（欄・details なし）、DB のほかの失敗＝503 E-PAGE-003。opsErrorReply のログは `[ops] <where> の DB が失敗した（<SQLSTATE>）` だけ（例外の文・値を出さない）
- 答えの形は今の入口の err と同じ（`{ error: "forbidden", code: "FORBIDDEN" }`・`{ error: "not_found", code: "NOT_FOUND" }`・`{ error: "unavailable", code: "E-PAGE-003" }`）

## 申し送り

- K-963〜K-995（運営の口の葉）：DB の関数は `app.ops_<名前>`・頭で `perform app.ops_require('<できること>')`（値は `v := app.ops_require(…)` でも可）・会社を指すなら次に `perform app.ops_target(p_tenant)`・書くなら `perform app.record_ops_audit(…)`。口は `opsTx` の中で呼び、例外は `opsErrorReply` で答える
- K-945：`app.ops_setup_consume` は台帳 EXEMPT に入れた（ログインの前に呼ぶ）。名前を変えるなら台帳も直す
- 後の葉で、運営の記録に残さない書き込みを持つ関数（例：期限を過ぎたお知らせの印・照合落ちの確かめの印だけを書く関数）を足すと、検査の「書くなら record_ops_audit」で赤になる。そのときは検査を緩めず、その関数を台帳 `EXEMPT` に理由つきで足す（理由の無い足しはしない）。記録に残す操作（D-156.48）なら record_ops_audit を呼ぶ形にする
